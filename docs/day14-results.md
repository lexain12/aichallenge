# День 14: инварианты и ограничения состояния

## Что реализовано

- Правила с ID и текстом сохраняются отдельно от истории сообщений в SQLite по `(user_id, task_id)`; команды `/invariant add`, `list`, `remove` работают локально, без вызова модели.
- Общие правила из `[[invariants]]` в `deepseek.toml` действуют для всех адресов, не записываются в SQLite и имеют приоритет при совпадении ID. CLI запрещает изменять такие ID без завершения сессии.
- В каждый обычный запрос при наличии правил добавляется отдельный `invariants`-блок, исключённый из compaction.
- `InvariantChecker` стоит первым среди response checkers. Он возвращает строгое `allow` либо `deny` с существующими ID и конкретными причинами. При `deny` advisory continuation checker не запускается.
- Ответ с активными инвариантами буферизуется до проверки. Запрещённый или непроверенный кандидат не выводится и не сохраняется; приложение само формулирует отказ из сохранённых правил и валидированного вердикта.
- Предложенные `StartNewTask` и `ReplanCurrent` проверяются до изменения workflow state. При конфликте новая задача/этап не создаются.
- Вызовы инвариант-чекера учитываются в общем token budget при наличии provider usage. Если usage отсутствует, дальнейшая автономность останавливается по прежнему правилу бюджета.

## Как проверить

```text
cargo run -- --user alice --task parser-project
/invariant add STACK Использовать только Rust
/invariant list
Разработай backend на Go
/task
```

Ожидается отказ с `STACK`; `/task` не должен показывать новую задачу. После допустимого запроса можно попросить `replan` на Go: ID/revision плана и текущий этап должны остаться прежними. Удаление правила через `/invariant remove STACK` снимает ограничение.

Автоматические тесты проверяют хранение и изоляцию scope, строгий формат вердикта, порядок checker-ов, отказ до вывода и сохранения ответа, отказ до создания задачи/replan, поведение при невалидном вердикте, присутствие блока в запросе, а также запрет обхода через `workflow.enabled = false`.

## Граница первой версии

Проверка смыслового конфликта зависит от LLM и может ошибаться. Правила нельзя считать формальными инвариантами базы данных. Мы проверяем кандидат ответа и некоторые предложения изменения workflow до commit, но не проводим отдельную проверку конечного состояния после каждого controller patch/handoff. Если для правила возможна точная проверка (например, стек из фиксированного списка), следующий шаг — детерминированный checker в том же блокирующем префиксе pipeline и отдельные тесты на фактическую проекцию состояния.

Локальный текст отказа сейчас выводится в текущем запуске, но не записывается как assistant-message в историю диалога. Поэтому после перезапуска виден сохранённый допустимый контекст, а сам отказ не воспроизводится в replay. Это отдельное улучшение протокола хранения, не защита от обхода инвариантов.
