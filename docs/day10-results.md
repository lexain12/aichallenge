# День 10: сценарий сравнения стратегий

Этот файл фиксирует один сценарий и одинаковую методику проверки. Числа и
оценки намеренно не выдуманы: таблица остаётся незаполненной до реальных
диалогов с DeepSeek.

## Подготовка

Для каждого режима используйте отдельную пустую базу и один и тот же system
prompt, модель, temperature и лимиты. В `deepseek.toml` меняйте только
`context.strategy`:

```toml
[context]
strategy = "sliding_window" # затем sticky_facts, branching и summary
keep_last_messages = 6
compact_after_prompt_tokens = 1200
summary_max_tokens = 512
facts_max_tokens = 512
```

Запускайте режимы по очереди:

```bash
cargo run -- --db /tmp/day10-sliding.sqlite3
cargo run -- --db /tmp/day10-facts.sqlite3
cargo run -- --db /tmp/day10-branching.sqlite3
cargo run -- --db /tmp/day10-summary.sqlite3
```

Удаляйте или переименовывайте прежнюю тестовую базу до повторного прогона,
чтобы накопленный usage и история не смешивались с новым результатом.

## Одинаковый сценарий: собираем ТЗ

Отправьте следующие 12 сообщений без смысловых изменений:

1. Мы проектируем Telegram-бота для записи в небольшую стоматологию.
2. Цель первой версии — снизить нагрузку на администратора, а не продавать
   дополнительные услуги.
3. Пользователи: пациенты клиники; интерфейс только на русском языке.
4. Ограничение: запуск за четыре недели командой из одного backend-разработчика.
5. Бот должен показать свободные слоты, записать пациента и отменить запись.
6. Не включай оплату, программу лояльности и медицинские рекомендации.
7. Интеграция с расписанием пока через REST API клиники; формат API ещё не
   согласован.
8. Для подтверждения записи нужен номер телефона и явное согласие на обработку
   персональных данных.
9. Администратор должен получить уведомление, если API расписания недоступен.
10. Приоритеты: сначала корректность записи, затем скорость ответа, затем
    внешний вид сообщений.
11. Составь черновик ТЗ: цель, роли, функциональные и нефункциональные
    требования, ограничения и открытые вопросы.
12. Проверь свой черновик: перечисли все ранее заданные запреты и критерии
    приоритета, затем исправь пропуски.

После сообщения 6 и после сообщения 12 выполните `/stats` и сохраните вывод.

### Вариант для branching

После сообщения 6 выполните `/branch` и запишите ID новой ветки. В исходной
ветке продолжите сообщениями 7–12. Затем выполните `/switch ID` и в новой ветке
замените сообщения 7–10 следующими четырьмя:

1. Расписание ведётся вручную администратором прямо в интерфейсе бота.
2. Для записи достаточно Telegram ID; номер телефона не запрашиваем.
3. При конфликте слотов бот предлагает три ближайших альтернативы.
4. Приоритеты: сначала срок запуска, затем удобство администратора, затем
   полнота функций.

После этого отправьте исходные сообщения 11–12. Проверьте, что каждая ветка
опирается только на собственные решения после checkpoint.

## Как оценивать

- **Качество:** полнота финального ТЗ и отсутствие придуманных требований.
- **Стабильность:** сохранены ли цель, срок, состав команды, язык, запреты,
  персональные данные и порядок приоритетов.
- **Токены:** три строки `/stats` — `Ответы`, `Summary`, `Facts` — и общий итог.
- **Удобство:** нужны ли повторения, понятны ли границы памяти и переключение
  веток, предсказуем ли результат.

Для качества и стабильности используйте шкалу 1–5 и рядом записывайте конкретные
потерянные или искажённые факты. Одна оценка без примеров малоинформативна.

### Объективный чек-лист финального ответа

- [ ] Цель — снижение нагрузки на администратора, без продажи дополнительных
  услуг.
- [ ] Пользователь — пациент клиники; язык — только русский.
- [ ] Срок — четыре недели; команда — один backend-разработчик.
- [ ] Есть просмотр слотов, создание и отмена записи.
- [ ] Не добавлены оплата, лояльность и медицинские рекомендации.
- [ ] Указана REST-интеграция и открытый вопрос о формате API.
- [ ] Для записи нужны телефон и явное согласие на обработку персональных данных.
- [ ] При недоступности API уведомляется администратор.
- [ ] Приоритеты сохранены в порядке: корректность, скорость, внешний вид.
- [ ] ТЗ содержит цель, роли, функциональные и нефункциональные требования,
  ограничения и открытые вопросы.

Каждый пункт оценивайте как `да`, `частично` или `нет`. Для ветки после
`/switch` применяйте её изменённые требования вместо трёх конфликтующих пунктов
про REST API, телефон и приоритеты.
