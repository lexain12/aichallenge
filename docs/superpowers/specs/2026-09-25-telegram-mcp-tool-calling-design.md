# Telegram MCP и tool calling в агенте

## Зачем это нужно

Day 16 добавил отдельный клиент, который подключается к удалённому MCP ВкусВилла,
выполняет `tools/list` и печатает результат. Основной агент при этом не знает об
MCP: он не передаёт инструменты в DeepSeek, не принимает `tool_calls`, не вызывает
`tools/call` и не возвращает результат модели.

Day 17 должен закрыть обе половины интеграции. Нужен локальный Telegram MCP-сервер
с тремя инструментами и общий tool-calling loop внутри Rust-агента. Telegram —
первый полноценный сервер, но агент не должен содержать Telegram-специфичный код:
следующий Streamable HTTP MCP подключается записью в конфигурации.

## Границы

В изменение входят:

- отдельный Python MCP-сервер для пользовательского Telegram-аккаунта;
- Streamable HTTP endpoint на локальном интерфейсе;
- `list_chats`, `read_chat` и `send_message`;
- общий реестр Streamable HTTP MCP-серверов в Rust;
- преобразование MCP tool definitions в DeepSeek function tools;
- полный цикл `DeepSeek tool_call → MCP tools/call → DeepSeek tool result`;
- несколько последовательных tool-раундов в одном ответе;
- безопасная диагностика и SQLite-аудит исполнений;
- интеграция с текущими workflow, invariant checks и token budget;
- локальные проверки и реальный end-to-end через Telegram и DeepSeek.

Не входят: stdio transport, Docker, Telegram Bot API, медиафайлы, MCP resources,
prompts и sampling, динамические `tools/list_changed`, автоматическое подтверждение
отправки человеком и поддержка нетекстовых MCP-результатов в DeepSeek Chat
Completions. `send_message` исполняется по решению модели без отдельного
подтверждения пользователя. Это разрешено протоколом, но осознанно не следует
рекомендации MCP оставлять человеку возможность отклонить побочный эффект.

## Выбор подхода

Рассмотрены три варианта:

1. Общий MCP-слой в Rust и отдельный Telegram MCP на Python. Rust остаётся MCP
   Host, а Python использует существующую Telethon session string.
2. Реализовать Telegram-клиент и сервер на Rust. Это потребует другой Telegram-
   библиотеки, отдельной авторизации и несовместимого с Telethon формата сессии.
3. Поставить между агентом и серверами отдельный MCP gateway. Он унифицирует
   подключения, но создаёт лишний сервис и точку отказа для учебного проекта.

Выбран вариант 1. Он использует имеющуюся авторизацию, сохраняет Telegram за
стандартной MCP-границей и не усложняет текущий Rust-проект инфраструктурой.

## Компоненты и ответственность

### Telegram MCP-сервер

Отдельный Python-проект использует официальный MCP SDK и Telethon. Он читает
`TELEGRAM_API_ID`, `TELEGRAM_API_HASH` и `TELETHON_SESSION_STRING` только из
environment, проверяет авторизацию через Telegram и поднимает Streamable HTTP
endpoint `http://127.0.0.1:8000/mcp`. Секреты не передаются аргументами командной
строки, не возвращаются инструментами и не печатаются в логах или traceback.
Отдельный `TELEGRAM_USER_ID` не нужен: сервер определяет текущий аккаунт через
`get_me()`. Day 17 не добавляет сетевую аутентификацию MCP, потому что endpoint
слушает только loopback и не должен публиковаться на внешнем интерфейсе.

Сервер запускается отдельно от Rust CLI. Агент не управляет его процессом, а
подключается к настроенному URL. Docker для Day 17 не нужен.

### MCP Registry в Rust

Реестр создаёт отдельный MCP client для каждого настроенного сервера, выполняет
`initialize` и `tools/list`, валидирует объявления и хранит маршрут от имени,
видимого модели, к паре `(server, original_tool_name)`. Агент не содержит веток
для Telegram, ВкусВилла или другого конкретного сервера.

Имена для DeepSeek формируются как `<server>__<tool>`, например
`telegram__read_chat`. Реестр хранит исходное имя и при вызове отправляет серверу
`read_chat`, а не namespaced-вариант. Имена проверяются на ограничения провайдера;
необратимая нормализация или коллизия после нормализации останавливает запуск с
понятной ошибкой.

Настроенный, но недоступный сервер считается ошибкой конфигурации. Агент не
стартует молча с неполным набором инструментов.

### DeepSeek tool-calling client

Chat Completions request получает необязательный массив `tools`. Обычный
потоковый ответ больше не представляется только строкой:

```text
AssistantTurn
├── FinalText { content, usage }
└── ToolCalls { calls, usage }
```

Клиент собирает фрагменты `tool_calls` по `index`, сохраняет provider call ID,
имя функции и конкатенирует части JSON arguments. Аргументы разбираются только
после завершения потока. Пустой `content` допустим для ответа с tool calls, но
пустой финальный текст остаётся ошибкой.

Внутреннее представление provider-сообщений поддерживает:

- обычные `system`, `user` и текстовые `assistant` сообщения;
- `assistant` с массивом `tool_calls`;
- `tool` с соответствующим `tool_call_id` и строковым content.

Это представление отделяется от существующего долговременного `Message`, чтобы
не протащить provider-specific поля во все слои памяти и workflow.

### Tool loop агента

Перед первым обычным ответом агент передаёт DeepSeek обнаруженные tool
definitions. Для каждого MCP Tool преобразуются `name`, `description` и
`inputSchema` в DeepSeek function name, description и parameters.

Если модель возвращает финальный текст, агент продолжает существующую обработку.
Если модель возвращает tool calls, агент:

1. сохраняет assistant tool-call message во временном provider transcript;
2. проверяет имя, JSON arguments, лимиты и повтор provider call ID;
3. маршрутизирует вызов через MCP Registry;
4. преобразует MCP `CallToolResult` в строковое сообщение роли `tool`;
5. повторно вызывает DeepSeek с теми же definitions и дополненным transcript;
6. повторяет цикл до финального текста или лимита.

`structuredContent`, если он есть, сериализуется как JSON. Иначе текстовые
элементы `content` объединяются в предсказуемом порядке. Нетекстовые элементы,
которые нельзя представить в Chat Completions, дают явный tool error, а не
молча отбрасываются.

За один пользовательский запрос разрешено не более восьми tool-раундов.
Несколько read-only вызовов из одного ответа можно выполнять параллельно;
write-вызовы выполняются последовательно. Результаты возвращаются модели в
исходном порядке. Повторный `tool_call_id` в одном запросе не исполняется.

## Контракты Telegram tools

### `list_chats`

Вход:

```json
{
  "query": "необязательная строка поиска",
  "limit": 100
}
```

`query` фильтрует названия и username без учёта регистра. `limit` по умолчанию
равен 100 и не может превышать 200. Результат:

```json
{
  "chats": [
    {
      "chat_id": "-1001234567890",
      "title": "Название чата",
      "username": "optional_username",
      "kind": "private|group|channel|bot",
      "is_self": false
    }
  ]
}
```

Telegram ID сериализуются строками, чтобы не терять точность в JSON-клиентах.
`is_self` однозначно отмечает Saved Messages текущего аккаунта.

### `read_chat`

Вход:

```json
{
  "chat": "-1001234567890",
  "limit": 20
}
```

`chat` принимает зарезервированный self-alias `me`, предпочтительный `chat_id`
из `list_chats`, точный username или точное название без учёта регистра. Лимит
по умолчанию равен 20, максимум 100. Сервер выбирает последние N сообщений и
возвращает их от старого к новому:

```json
{
  "chat": {
    "chat_id": "-1001234567890",
    "title": "Название чата"
  },
  "messages": [
    {
      "message_id": 123,
      "sent_at": "2026-09-25T10:30:00Z",
      "sender_id": "456",
      "sender_name": "Имя",
      "text": "Текст сообщения",
      "outgoing": false,
      "reply_to_message_id": null
    }
  ]
}
```

Сервер возвращает текст и метаданные, но не скачивает медиа. Сообщение без
текста может быть представлено пустым текстом с сохранёнными метаданными.

### `send_message`

Вход:

```json
{
  "chat": "-1001234567890",
  "text": "Текст сообщения"
}
```

Результат успеха:

```json
{
  "sent": true,
  "chat_id": "-1001234567890",
  "message_id": 124,
  "sent_at": "2026-09-25T10:31:00Z"
}
```

Разрешение `chat` выполняется строго в порядке: зарезервированное `me`, точный
ID, точный username, точное название без учёта регистра. Если одному названию
соответствуют несколько диалогов, сервер возвращает `ambiguous_chat` с
безопасным списком кандидатов и ничего не отправляет. Нечёткий поиск для
отправки запрещён. `text` должен быть непустым и помещаться в один текстовый
Telegram message; сервер отправляет plain text, не разбивает его и не применяет
`parse_mode`.

После неоднозначного сетевого сбоя `send_message` не повторяется автоматически:
сервер возвращает `delivery_unknown`. Модель может прочитать чат и проверить
результат, но повторная отправка остаётся новым осознанным tool call и всё ещё
может создать дубликат.

Ожидаемые безопасные коды ошибок: `chat_not_found`, `ambiguous_chat`,
`telegram_unauthorized`, `rate_limited` и `delivery_unknown`. Внешние исключения
не должны раскрывать credentials или traceback.

`list_chats` и `read_chat` объявляются read-only, `send_message` — write и
неидемпотентным. Аннотации стороннего MCP не считаются достаточной границей
безопасности: отсутствующая или неизвестная классификация трактуется как write.

## Конфигурация

```toml
[mcp]
connect_timeout_seconds = 10
call_timeout_seconds = 30
max_tool_rounds = 8

[[mcp.servers]]
name = "telegram"
url = "http://127.0.0.1:8000/mcp"

# [[mcp.servers]]
# name = "vkusvill"
# url = "https://mcp.vkusvill.ru/mcp"
```

Имена серверов непустые и уникальные, URL должен быть HTTP(S), таймауты и лимит
раундов положительные. Неизвестные поля отклоняются по существующему правилу
конфига. Если серверы не заданы, MCP выключен и поведение агента остаётся
прежним.

## Workflow и инварианты

Tools доступны только обычной модели, формирующей пользовательский ответ.
Interpreter, invariant checker, continuation checker, handoff, summary и facts
работают без tools и сохраняют свои детерминированные контракты.

Каждый DeepSeek-вызов tool loop учитывается в суммарном usage обычного ответа и
`max_autonomous_tokens`, но не считается отдельным автономным workflow turn.
`last_usage` показывает сумму provider-reported usage всех раундов этого
пользовательского запроса. Отсутствующий usage сохраняет существующую семантику
неполной оценки бюджета.

Финальный текст проходит существующие blocking и advisory checker-ы. Это уже не
может отменить выполненный побочный эффект, поэтому write-вызов до исполнения
проверяется существующим invariant checker как кандидат действия с именем
инструмента и аргументами. Разрешённый write выполняется сразу, без human
confirmation. Отказ или недоступность checker-а не вызывает MCP. В режиме без
инвариантов дополнительного модельного вызова нет.

Tool content считается недоверенными данными. Он добавляется только в `tool`
message и не может заменить системные блоки, протокол этапа или правила проекта.

## Хранение и восстановление

Существующая таблица `messages` и её ограничение ролей `user|assistant` не
меняются. В ней сохраняются человеческий ввод и только финальный текст модели.
Промежуточные assistant tool calls и tool results живут во временном provider
transcript текущего запроса и не подмешиваются в последующие пользовательские
ходы. Финальный ответ должен содержать информацию, которую модель считает
нужной сохранить в разговоре.

Для безопасного аудита добавляется отдельная таблица `tool_executions`:

```text
dialog_id
input_message_id
tool_call_id
server_name
tool_name
arguments_hash
status: started | succeeded | failed | uncertain
is_error
error_code
started_at
finished_at
```

Пара `(dialog_id, tool_call_id)` уникальна. До обращения к MCP сохраняется
`started`, после однозначного результата — `succeeded` или `failed`, после
потери определённости для write-вызова — `uncertain`. Сырые arguments, tool
results и прочитанные Telegram-сообщения в SQLite не сохраняются. Они могут
попасть в локальный JSONL только при явном `debug.log_payloads = true`; обычная
диагностика хранит имена, статусы, размеры, коды ошибок и usage.

Прерванный tool loop автоматически не возобновляется после рестарта. Записи
`started` и `uncertain` не исполняются повторно самим recovery. Новый
пользовательский запрос создаёт новые model call IDs и не может математически
гарантировать отсутствие повторной отправки; при `delivery_unknown` нужно
сначала прочитать чат.

Миграция только добавляет таблицу и индексы, не переписывая старые сообщения.
Branching копирует долговременный диалоговый checkpoint, но не переносит
незавершённые исполнения как работу новой ветки. In-memory Agent ведёт
дедупликацию только в памяти.

## Ошибки и наблюдаемость

- Невалидные JSON arguments и неизвестное tool name не достигают MCP.
- MCP `isError` становится tool result, чтобы модель могла объяснить ошибку или
  выбрать другой инструмент.
- Превышение `max_tool_rounds` завершает запрос контролируемой ошибкой без
  следующего provider call.
- Read-only операция может получить ограниченный транспортный retry, но
  write-вызов после начала отправки автоматически не повторяется.
- Сбой одного вызова не раскрывает URL credentials, session string, Telegram
  API hash или полный traceback.
- CLI показывает понятные события начала/завершения инструмента, но не печатает
  приватный payload вместо ответа модели.

## Проверка результата

Детерминированные локальные тесты покрывают конфигурацию, преобразование схем,
namespacing и коллизии, сборку потоковых tool calls, несколько вызовов, неверный
JSON, лимит раундов, usage, invariant gate, SQLite migration и защиту от
повторного write call ID. Эти тесты не требуют реальных credentials и позволяют
локализовать ошибки, которые невозможно стабильно вызвать через внешние API.

Итоговая интеграция проверяется на собранной системе:

1. Запустить настоящий Telegram MCP с текущими environment variables.
2. Подключить собранный Rust MCP Registry, выполнить `initialize` и `tools/list`.
3. Через Registry вызвать настоящие `list_chats` и `read_chat` с `chat = "me"`.
4. Запустить Rust-агента с настоящим DeepSeek и Telegram MCP.
5. Попросить модель найти и прочитать Saved Messages через alias `me`.
6. Попросить отправить уникальный маркер `AIchallenge Day 17 smoke <uuid>`.
7. Снова прочитать «Избранное» через модель и убедиться, что маркер появился
   ровно один раз.
8. Проверить `tool_executions`, сохранение финального ответа и восстановление
   диалога после перезапуска.
9. Остановить MCP и проверить понятную ошибку подключения.

`send_message` не входит в обычный автоматический набор. Единственная реальная
тестовая отправка направляется в Saved Messages текущего аккаунта; людям,
группам и каналам тест ничего не отправляет и созданный маркер не удаляет.

Полный end-to-end зависит от Telegram, DeepSeek, сети и решения модели вызвать
инструмент. Если внешний компонент недоступен, локальные тесты могут пройти, но
полная приёмка не считается завершённой и это должно быть явно отражено в
результатах.

Day 17 готов, когда Telegram MCP соответствует Streamable HTTP MCP, модель
самостоятельно использует все три инструмента через общий Rust tool loop,
сторонний Streamable HTTP MCP добавляется конфигурацией, старые режимы и тесты
не ломаются, а секреты не попадают в код, SQLite, stdout или обычные логи.
