# DeepSeek CLI

Один интерактивный чат с агентом на Rust. Ответ печатается по мере генерации,
а сообщения сохраняются в SQLite и переживают перезапуск программы.
Реплики пользователя и DeepSeek выделяются разными фоновыми полосами.

## День 9: компрессия истории

Агент хранит в SQLite полную исходную историю, но при росте контекста перестаёт
отправлять старые реплики в каждый запрос. Вместо них DeepSeek создаёт одно
накопительное summary. Обычный запрос после сжатия выглядит так:

```text
system prompt → summary старой части → последние N исходных сообщений → новый вопрос
```

Компактер запускается после успешного ответа, если полученный от DeepSeek
`prompt_tokens` достиг `compact_after_prompt_tokens`. Пересёкший порог запрос
ещё получает полный доступный контекст; summary используется со следующего
вопроса. Локальной приблизительной оценки токенов нет. Если API не вернул usage,
на этом ходе запускать компактер небезопасно, поэтому он ждёт следующего
подходящего ответа.

При первом сжатии summary строится из старого префикса истории. При следующем
вызове компактер получает предыдущее summary и только новые сообщения, которые
теперь вышли за пределы сохраняемого raw-tail. Новое summary заменяет старое
только после успешного атомарного сохранения. Ошибка API не ломает уже полученный
пользовательский ответ; агент продолжает с полной историей. Ошибка SQLite
остаётся фатальной, чтобы процесс не работал с несохранённым состоянием.

В базе остаются все оригинальные сообщения и только одно текущее summary с его
границей и накопленными расходами компактинга. Предыдущие тексты summary не
хранятся: для восстановления достаточно полной истории, а пооперационный аудит
можно включить через JSONL-лог.

Настройки находятся в общем `deepseek.toml`:

```toml
[context]
enabled = true
compact_after_prompt_tokens = 6000
keep_last_messages = 10
summary_max_tokens = 1024

[debug]
# log_path = "deepseek-debug.jsonl"
log_payloads = false
```

Summary создаётся той же моделью с температурой `0`, отключённым thinking и
отдельным `summary_max_tokens`. `top_p` и `stop` обычного ответа к служебному
вызову не применяются.

Команда `/stats` не вызывает API и показывает накопленные значения диалога:

```text
Контекст · полная история: 24 · покрыто summary: 14 · дословно: 10
Ответы · вход: 12000 · выход: 2000 · всего: 14000
Сжатие · вход: 5000 · выход: 600 · всего: 5600
API всего · 19600
```

Токены ответов и служебного сжатия разделены, а `API всего` учитывает оба вида
вызовов. Если завершённый вызов не содержит usage, `/stats` отдельно показывает
число таких вызовов и не считает их нулями. Нижний footer по-прежнему относится
только к последнему пользовательскому запросу: после активации summary его
`prompt_tokens` должен уменьшиться естественным образом.

### Ручное сравнение

Подготовьте одинаковую последовательность вопросов и используйте разные базы.
Сначала отключите компрессию и выполните сценарий:

```toml
[context]
enabled = false
```

```bash
cargo run -- --db no-compression.sqlite3
```

Затем включите её и повторите вопросы с другой базой:

```bash
cargo run -- --db compression.sqlite3
```

В конце каждого запуска выполните `/stats`. Сравнивайте качество ответов вручную,
а расход — по строкам «Ответы», «Сжатие» и «API всего». Для быстрой демонстрации
можно временно поставить порог `100`; это намеренно неэффективное значение для
обычной работы.

### Диагностика

При интерактивном запуске начало и результат компактинга видны как короткие
статусные сообщения. Если задан `debug.log_path`, JSONL-файл дописывается и
flush-ится после каждого события: там видны состав запроса, граница summary,
решение о сжатии и usage. По умолчанию сохраняются только роли и длины текстов.
`log_payloads = true` добавляет точный массив `messages`; это может записать
чувствительный текст диалога. API-ключ редактируется в любом режиме. Ошибка
записи лога показывает одно предупреждение и не прерывает работу агента.

## День 8: токены из API

Пока ожидается первый текст ответа, в строке статуса отображается «Думаю…».
В iTerm2 справа от текста проигрывается GIF белой лошади на чёрном фоне высотой в одну
текстовую строку. Файл встроен в исполняемый файл; дополнительные программы
и файлы из Downloads для запуска не нужны. При появлении первого непустого
фрагмента ответа или завершении запроса индикатор убирается.
Статистика токенов появляется только после завершения ответа.

В других терминалах, внутри tmux/screen и в очень узком окне используется
текстовый индикатор. При перенаправлении вывода индикатор отключён.
`NO_COLOR=1` отключает оформление текста, но сохраняет анимацию в iTerm2.

Внизу чата, над приглашением ввода, отображается одна общая строка
статистики последнего запроса (приглушённая в цветном терминале):

```text
Токены · Вход: 2400 · Выход: 350 · Всего: 2750
```

- **Вход** — `prompt_tokens`: system prompt, вся переданная история и новый вопрос.
- **Выход** — `completion_tokens`: генерация модели, включая рассуждения,
  если они входят в статистику провайдера.
- **Всего** — `total_tokens` из API. Это расход одного вызова,
  не сумма всех прошлых запросов и не размер сохранённой истории.
- Если API прислал `completion_tokens_details.reasoning_tokens`, рядом показано
  «Рассуждения». Это часть выхода, повторно к итогу она не прибавляется.

Во время ожидания и печати ответа статистика токенов скрыта; после
завершения появляются свежие счётчики. Перед следующим сообщением прежняя строка
убирается. При восстановлении диалога статистика появляется один раз внизу,
без подписей под старыми ответами. В узком окне строка обрезается с многоточием,
чтобы не занимать несколько рядов. Если API не прислал usage, показано **«нет данных API»**.
Нулевые значения отображаются только когда API действительно вернул нули.
Повторные события usage заменяют предыдущие значения для текущего вызова,
не суммируются. Старые показатели не переносятся на новый запрос или ошибку.

Статистика сохраняется вместе с полным ответом в одной транзакции SQLite
и восстанавливается при `--resume-last` / `--resume ID`.
При перенаправлении вывода обновления строки отключены: выводится только
одна итоговая строка при выходе, без управляющих последовательностей терминала. Для баз седьмого дня
автоматически создаётся дополнительная таблица `message_usage`; старые сообщения
сохраняются; если последняя реплика не содержит usage, строка показывает «нет данных API». Метаданные токенов не отправляются
модели как часть истории. Если незавершённый запрос успел вернуть usage, она
выводится для этого вызова, но без завершённого ответа в базу не записывается.

Раздельных счётчиков для нового вопроса и прошлой истории пока нет: API возвращает
их общий вход. Локального приблизительного подсчёта по символам здесь нет.
Флаг `include_usage` в конфигурации по умолчанию включён.
[Описание usage в DeepSeek API](https://api-docs.deepseek.com/api/create-chat-completion/).

## Сохранение и восстановление диалогов

```bash
cargo run                         # Новый диалог
cargo run -- --resume-last         # Продолжить последний активный диалог
cargo run -- --list-dialogs        # Список: ID, время UTC, число сообщений, первый вопрос
cargo run -- --resume 3            # Продолжить диалог с ID 3
cargo run -- --db /path/chats.sqlite3 --resume-last
```

По умолчанию база — `dialogs.sqlite3` **в текущем рабочем каталоге**.
Для общей истории при запуске из разных каталогов передавай один абсолютный
путь через `--db`. Родительский каталог должен существовать. SQLite встроена
в приложение; отдельный сервер базы данных не нужен. База и её служебные
файлы исключены из Git.

Каждый обычный запуск начинает новый диалог. Запись о нём создаётся с первым
непустым сообщением; запуск и выход без сообщений не засоряют список.
`--resume-last` выбирает диалог с последней сохранённой репликой, а не просто
последний созданный. При восстановлении предыдущие сообщения выводятся
в том же окне, и можно продолжать ввод. Если диалогов нет, флаг выдаёт понятную
ошибку; запусти программу без него. `--list-dialogs` работает без API-ключа и
конфигурационного файла. Флаги списка и восстановления несовместимы друг с другом.

Сообщения сохраняются инкрементально, отдельными транзакциями:

1. Вопрос пользователя записывается **до отправки запроса в API**.
2. Полный непустой ответ записывается после успешного завершения потока.
3. Полная история остаётся сохранённой, а API получает либо все реплики, либо
   активное summary и непокрытый хвост в исходном порядке.

При ошибке API или принудительном завершении процесса уже записанный вопрос
остаётся в базе. Частичный, пустой или обрезанный ответ в историю не попадает:
отображение фрагмента на экране ещё не означает сохранение полного сообщения.
Запись не откладывается до выхода из программы. Ошибка базы останавливает
программу с сообщением об ошибке. Если другой процесс успел изменить тот же
диалог, устаревшая сессия также останавливается с предложением восстановить её.

`/clear` очищает текущий контекст и отсоединяет агента от старого диалога;
старые сообщения остаются в базе, следующий вопрос создаст новый диалог.
System prompt при очистке сохраняется.

## Агент в коде

`Agent` в `src/agent.rs` владеет API-клиентом, историей и необязательным
`DialogStore`. `DialogStore` в `src/dialog.rs` отвечает за SQLite.

```rust
use deepseek_cli::{agent::Agent, config::Config, dialog::DialogStore};
use std::path::Path;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = Config::load(
        Path::new("deepseek.toml"),
        std::env::var("DEEPSEEK_API_KEY").ok(),
    )?;
    let path = Path::new("dialogs.sqlite3");
    let store = DialogStore::open(path)?;
    let mut agent = Agent::with_store(&config, store)?
        .with_prompt("Объясни ownership в Rust");
    println!("{}", agent.run().await?);
    let id = agent.dialog_id().expect("Первое сообщение сохранено");
    drop(agent);

    let store = DialogStore::open(path)?;
    let mut agent = Agent::from_dialog(&config, store, id)?;
    println!("{}", agent.run_with_prompt("Теперь покажи пример").await?);
    Ok(())
}
```

- `Agent::with_store(...)` создаёт агента с сохранением сообщений.
- `Agent::from_dialog(config, store, id)` восстанавливает исходный system prompt
  и сообщения. API-ключ, модель и параметры запросов берутся из текущего конфига;
  настройки подключения и ключ не записываются в таблицы диалогов.
- `run()` использует промпт, заданный через `with_prompt(...)`;
  `run_with_prompt(...)` отправляет новое сообщение, сохраняя промпт по умолчанию.
- `run_streaming(prompt, callback)` передаёт `AgentEvent`: фрагменты ответа,
  usage и события начала, завершения или ошибки компактинга.
- `history().messages()` возвращает сохранённые реплики для чтения;
  `message.usage()` — статистику вызова, создавшего ответ.
- `last_usage()` — последняя полученная статистика текущего запроса;
  после восстановления берётся из последней реплики, если она содержит usage.
- `context_stats()` — полная граница контекста и накопленный расход обычных и
  служебных вызовов.
- `Agent::new(...)` остаётся вариантом без базы, как в шестом дне:
  он хранит в памяти только успешно завершённые пары сообщений.

Пустые промпты отклоняются до записи и вызова API. Полная история остаётся
доступной через `history()`, даже когда в следующий API-запрос подставляется
summary.

## Сборка

```bash
cargo build --release
```

Готовый исполняемый файл: `target/release/deepseek-cli`. При желании его можно
установить в Cargo bin-каталог:

```bash
cargo install --path .
```

## Настройка

Создайте локальный конфиг из примера:

```bash
cp deepseek.example.toml deepseek.toml
```

Вставьте API-ключ в `api_key`. Файл `deepseek.toml` исключён из Git, однако его
всё равно следует считать секретным и не пересылать другим людям.

Ключ также можно передать переменной окружения; она имеет приоритет над файлом:

```bash
DEEPSEEK_API_KEY='your-key' deepseek-cli
```

Доступные параметры:

```toml
api_key = "replace-with-your-key"
base_url = "https://api.deepseek.com"
model = "deepseek-v4-flash"
system_prompt = "You are a helpful assistant."
temperature = 1.0
max_tokens = 4096
timeout_seconds = 120

[context]
enabled = true
compact_after_prompt_tokens = 6000
keep_last_messages = 10
summary_max_tokens = 1024

[debug]
# log_path = "deepseek-debug.jsonl"
log_payloads = false
```

Кроме ключа, все поля необязательны и принимают показанные значения по
умолчанию. Другой файл можно выбрать явно:

```bash
deepseek-cli --config /path/to/config.toml
```

## Использование

```text
$ deepseek-cli
you> Объясни ownership в Rust одним абзацем
assistant> ...ответ появляется постепенно...
you> /exit
```

Команды:

- `/clear` — начать новый диалог, сохранив прежний в базе;
- `/stats` — показать контекст и накопленные токены без вызова API;
- `/exit` или `/quit` — выйти;
- Ctrl+D — выйти.

Если запрос оборвался или API вернул ошибку, вопрос остаётся в истории,
а незавершённый ответ не сохраняется. Можно написать следующее сообщение: например,
«Ответь на предыдущий вопрос». Оно отправится вместе с сохранённым контекстом.

Цвета автоматически отключаются при перенаправлении вывода. В интерактивном
терминале их можно отключить вручную стандартной переменной `NO_COLOR`:

```bash
NO_COLOR=1 deepseek-cli
```
