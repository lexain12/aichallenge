# DeepSeek CLI

Один интерактивный чат с агентом на Rust. Обычно ответ печатается по мере генерации,
а сообщения сохраняются в SQLite и переживают перезапуск программы.
Реплики пользователя и DeepSeek выделяются разными фоновыми полосами.

`/debug` выводит локальный JSON-снимок: адрес диалога, выбранный профиль
пользователя (`active_profile`: ID, наличие, время обновления), полное текущее
workflow-состояние, статус обработки ответа, метрики контекста и активные
инварианты. Текст профиля в `/debug` не выводится. Команда не вызывает модель и не меняет задачу. Сырая история,
скрытые controller-сообщения и API-ключ не выводятся; goal, план и checkpoint
могут содержать текст проекта, поэтому не публикуйте этот вывод без проверки.

## День 14: инварианты проекта

Инварианты — обязательные правила проекта с явными ID. Правила для конкретного
проекта хранятся в SQLite отдельно от диалога по адресу `user ID + task ID`,
переживают перезапуск и не попадают под компактизацию истории. Изменять их можно
локальными командами:

```text
/invariant add STACK Использовать только Rust
/invariant add ARCH Сохранить монолитную архитектуру
/invariant list
/invariant remove ARCH
```

Общие правила можно задать и в `deepseek.toml`:

```toml
[[invariants]]
id = "STACK"
text = "Использовать только Rust"
```

Они действуют для всех `user ID + task ID`, открытых с этим конфигом, но не
копируются в SQLite. `/invariant list` показывает объединённый набор. При
совпадении ID действует правило из конфига; изменить или удалить его командой
CLI нельзя — приложение сообщает об этом и продолжает работу. Изменения TOML
подхватываются при следующем запуске.

При наличии правил ассистент получает отдельный системный блок с ними. Первый
checker в упорядоченном массиве проверяет полный кандидат ответа через LLM.
Пока он не разрешил ответ, текст буферизуется и не показывается; при отказе
следующие checker-ы не запускаются. Перед созданием новой workflow task и перед
`replan` тот же checker проверяет предложенное изменение до записи состояния.
Отказ показывает ID, текст правила и причину конфликта. Если checker недоступен
или вернул невалидный JSON, кандидат также не показывается и не сохраняется.

Если в `[debug]` задан `log_path`, каждый реально вызванный блокирующий checker
пишет отдельное JSONL-событие `workflow`: `check_target` (`start_new_task`,
`replan_current` или `candidate_response`), `outcome` (`allowed`, `denied`,
`unavailable`), `violation_ids` и категорию ошибки. Следующие checker-ы после
блокировки не запускаются, поэтому записей о них нет. При
`log_payloads = true` в `payload.invariant_violations` попадут подробные
причины, а для проверки ответа `checker_output` сохранит сырой вывод модели;
такой файл может содержать
конфиденциальные данные. При `false` причины остаются только в видимом отказе.
Отклонённый старт второй задачи логируется с `input_intent`, текущими
`input_phase`/`input_status` и `rejection_reason`: пока задача не дошла до
`done`, начать новую в том же диалоге нельзя.

Это проверка естественно-языковых правил моделью, а не формальное доказательство.
На данном этапе controller patch и handoff не проходят отдельную проверку
конечной проекции состояния: проверяется предшествующий им ответ. Для строгих
машинно-проверяемых ограничений потребуется отдельный детерминированный checker.
В persistent-режиме с правилами `workflow.enabled = false` отклоняется, чтобы
не открыть обход проверок через старый режим. [Сценарии и ограничения Day 14](docs/day14-results.md).

## День 15: согласование цели

Новая задача начинается в `goal_definition`. Первое сообщение задаёт рабочую
цель, которую можно обсудить и изменить. Когда формулировка готова, ассистент
выводит отдельную строку `Предлагаемая цель: <текст>`. Она остаётся предложением,
пока человек не подтвердит её следующим сообщением обычной фразой, например
«Да, утверждаю эту цель». Только после подтверждения открывается `planning`.
Уточнение вроде «Да, но без авторизации» должно продолжить обсуждение, а не
утвердить старую формулировку. После утверждения человек может попросить
«Вернись к обсуждению цели: ...»: текущий план сбрасывается, задача переходит
в новый этап `goal_definition`, а история остаётся в SQLite. `/task` показывает
рабочую или утверждённую цель, её revision и ID ожидающего предложения.

Классификация обычных фраз выполняется LLM и может ошибаться. Локальные
проверки не позволяют модели или checker-у самостоятельно утвердить цель,
перепрыгнуть этап или обойти инварианты, но они не доказывают, что семантически
неоднозначная фраза понята правильно. Отдельная проблема утверждения самого
плана после `planning` пока не решена.

## День 13: workflow tasks

После утверждения цели задача проходит `planning → execution → validation → done`.
Неуспешная валидация возвращает её в новый этап `execution`: у повторного
выполнения собственные ID и номер этапа. Одновременно в диалоге допустима
только одна незавершённая workflow task. После `done` человек может начать
следующую задачу в том же диалоге; история предыдущей остаётся в SQLite.

Перед обычным ответом интерпретатор предлагает типизированный intent по
сообщению человека. После полного ответа advisory-checker предлагает patch
состояния и `AwaitUser`, продолжение или переход. Приложение проверяет каждое
предложение: непустой план и критерии для начала выполнения, завершённые шаги
для валидации, наблюдаемые результаты по критериям для `done`. Заявление модели
о завершении само по себе не завершает задачу. Переходы `planning → validation`,
`execution → done` и `done → execution` отклоняются локально без обычного запроса.
Слова ниже — обычные сообщения интерпретатору, а не гарантированные команды
или способ обойти проверки:

```text
cargo run -- --user alice --task parser-project
Спроектируй парсер: согласуй план и критерии проверки.
/task
План принят, переходи к выполнению.
Реализация завершена, переходи к проверке.
Перепланируй текущую задачу с учётом потокового ввода.
```

`/task` — локальный read-only просмотр последнего сохранённого состояния:
номер и ID workflow task, phase, `active`/`paused`, revision плана, текущий шаг,
ожидаемое действие, номер этапа и состояние checker processing. Предложенный,
но отклонённый переход не показывается как выполненный. `--task parser-project`
по-прежнему выбирает namespace durable memory (`user ID + task ID`), а не ID
workflow task: несколько последовательных workflow tasks могут использовать
одну память проекта.

Ctrl+C отменяет текущую работу модели, отбрасывает незавершённый ответ,
сохраняет последнюю полную контрольную точку, ставит незавершённую задачу на
паузу и завершает CLI. Это действует во время интерпретации, обычного ответа,
checker, handoff и ожидания ввода. Если задача ещё не создана, ради паузы она
не создаётся. Полностью сохранённый ответ остаётся, даже если прерван его checker.

```text
cargo run -- --resume-last
/task
continue
```

Загрузка диалога сама по себе не возобновляет выполнение. Она может завершить
оставшийся advisory-checker и сохранить допустимый patch, но не создаёт
автономное продолжение и не снимает паузу. Только принятый человеческий
`Continue`, запрос перехода или явное перепланирование активирует задачу.
Continue сохраняет текущий этап и план; replan создаёт новый `planning` с тем
же ID задачи и новой revision. Controller не может возобновить паузу, начать
другую задачу или запросить replan. Пока текущая задача не завершена, запрос
начать другую отклоняется; для независимой задачи можно открыть новый диалог.

Обычный контекст собирается в порядке:

```text
base → user_profile → user_memory → task_memory → invariants → workflow_task
     → summary/facts текущего этапа (если нужны) → protocol текущего этапа
```

Блок `invariants` присутствует только когда для проекта заданы правила.
Старые задачи, raw-сообщения предыдущих этапов и полный handoff не подмешиваются
в запрос. Перед переходом отдельная модель готовит handoff; только проверенная
компактная проекция его полей становится checkpoint/планом/ожидаемым действием
нового этапа. Полный handoff и append-only журнал переходов остаются для аудита.
Summary и sticky facts ограничены текущим этапом. В branching-режиме ветка
получает независимую копию workflow-состояния и аудита.

Синтетические controller-инструкции хранятся как скрытые user-role строки с
отдельным происхождением. Они входят в protocol своего этапа, но скрыты в
replay и не используются как факты пользователя, профиль или durable memory.
Каждый автономный ответ CLI выводит отдельным assistant-блоком. Ошибка checker
или handoff сохраняет уже полученный ответ и останавливает автономную работу.
Метаданные диагностики видны без текста; `debug.log_payloads = true` явно
включает содержимое запросов, предложений, checkpoint и handoff в debug log.

### Настройки workflow

Все значения по умолчанию взяты из `src/config.rs`; секцию можно не указывать.
Workflow используется persistent-агентами. `enabled = false` оставляет старый
режим диалога; in-memory Agent продолжает работать без workflow.

| Ключ `[workflow]` | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `enabled` | `true` | Включить workflow в persistent-диалогах |
| `interpreter_model` | Текущий верхнеуровневый `model` | Разбор человеческого сообщения |
| `checker_model` | Текущий верхнеуровневый `model` | Проверка ответа и предложение продолжения |
| `handoff_model` | Текущий верхнеуровневый `model` | Передача состояния между этапами |
| `interpreter_max_tokens` | `512` | Лимит ответа интерпретатора |
| `checker_max_tokens` | `1024` | Лимит ответа checker |
| `handoff_max_tokens` | `2048` | Лимит ответа handoff-модели |
| `min_confidence` | `0.80` | Минимальная уверенность управляющего предложения |
| `max_autonomous_turns` | `8` | Число дополнительных обычных ответов после одного человеческого ввода |
| `max_autonomous_tokens` | `20000` | Бюджет provider-reported API tokens на этот цикл |

У верхнеуровневого `model` сейчас default `deepseek-v4-flash`. Явные имена
workflow-моделей не могут быть пустыми; лимиты должны быть положительными,
confidence — конечным числом от 0 до 1. Неизвестные ключи отклоняются.
Служебные вызовы используют temperature 0, выключенный thinking и без stop
sequences; их model/max_tokens задаются независимо от обычного ответа.

Бюджет учитывает interpreter, checker, handoff, обычные ответы, facts и summary.
При достижении лимита новые автономные вызовы не начинаются; текущий вызов и
checker уже сохранённого ответа могут превысить номинальную границу. При
отсутствии usage, повторном fingerprint состояния, низкой уверенности,
невалидном JSON или ошибке автономная работа останавливается. Лимит обновляется
после нового человеческого ввода. Это ограничитель планирования вызовов, а не
жёсткий предел счёта за уже выполненный запрос.

Приёмочные сценарии, проверки и намеренные ограничения:
[`docs/day13-results.md`](docs/day13-results.md).

## День 12: свободный профиль пользователя

У каждого `user ID` может быть один свободный Markdown-профиль с мягкими
предпочтениями. Схема не ограничивает профиль категориями: в одном документе
можно описать стиль общения, предпочитаемые технологии, обычный процесс работы
и любые другие настройки.

```markdown
# Предпочтения

Общайся кратко и по делу.
Для мобильных приложений предпочитай Android, Kotlin и Jetpack Compose.
Не добавляй архитектурные абстракции без практической необходимости.
```

Профиль можно заменить короткой строкой или импортировать из UTF-8 Markdown:

```text
cargo run -- --user alice --task mobile-app
/profile set Общайся кратко и по делу
/profile import ./profiles/alice.md
/profile
/profile clear
```

SQLite остаётся источником истины: файл нужен только во время импорта. Команды
профиля выполняются локально, не вызывают модель и не создают диалог. Ошибка
чтения, невалидный UTF-8 или пустой импорт оставляют прежний профиль без
изменений и не завершают REPL.

В `profiles/alice.md` задана мягкая аниме-манера, а в `profiles/bob.md` —
пиратская. Профиль выбирается по точному `user ID` (регистр важен):

```text
cargo run -- --user alice
cargo run -- --user bob
```

Без `--user` используется `default`, для него эти профили не действуют.

Перед каждым обычным запросом профиль загружается заново по `user ID` и
становится отдельным system-блоком `user_profile`. Поэтому изменение профиля
действует уже на следующий запрос и автоматически распространяется на все
задачи и диалоги того же пользователя. Другой пользователь его не видит.

Порядок контекста детерминирован:

```text
base → user_profile → user_memory → task_memory → conversation context
```

Профиль содержит мягкие значения по умолчанию. Явный текущий запрос и
task-specific контекст имеют приоритет. Жёсткие запреты и бизнес-инварианты не
являются профилем и остаются задачей будущего Day 14.

`user_profile` имеет `ContextScope::User` и `CompactionPolicy::Exclude`, поэтому
сам блок не передаётся summary-компактеру. Если его содержание повторилось в
обычной переписке, эта реплика всё равно может войти в conversation summary.
При `debug.log_payloads = false` в JSONL видны только безопасные метаданные
блока; содержимое профиля появляется в логах только при явном включении payload.

Два разных профиля, SQLite/debug-проверки и готовый сценарий записи видео:
[`docs/day12-results.md`](docs/day12-results.md).

## День 11: явные слои памяти

Day 11 разделяет контекст по адресу и сроку жизни:

```text
conversation = dialog ID; task = user ID + task ID; user = user ID
```

- **Conversation** — сообщения, cumulative summary и sticky facts одного
  диалога. Слой заполняется автоматически; старый raw-контекст можно заменить
  summary в запросе модели, но полная исходная история остаётся в SQLite.
- **Working** (`task`) — явные key-value записи пользователя для одной задачи.
  Они переживают новые диалоги и перезапуск процесса, но доступны только для
  той же пары `user ID + task ID`.
- **Long-term** (`user`) — явные key-value записи пользователя, общие для всех
  его задач и диалогов. Другой пользователь их не видит.

Новый scoped-диалог и операции с памятью:

```text
cargo run -- --user alice --task telegram-bot
/remember user response_language Russian
/remember task stack Rust
/memory
/forget task stack
```

`/remember user|task` и `/forget user|task` всегда явно называют изменяемый
слой. `/memory` показывает Conversation, Working и Long-term;
`/memory user` или `/memory task` оставляет только выбранный durable-слой.
Команды выполняются локально, не вызывают модель и записывают durable-память в
ту же SQLite-базу. Повторный `/remember` с тем же ключом заменяет значение.

Без `--user` и `--task` используются точные идентификаторы `default` и
`default`. При `--resume ID` или `--resume-last` всегда восстанавливается
сохранённый scope диалога. Явный конфликтующий `--user` или `--task` завершает
запуск локальной ошибкой до API-запроса. `--list-dialogs` показывает оба
идентификатора рядом с ID диалога.

В обычном запросе непустые durable-слои автоматически становятся отдельными
system-блоками `user_memory`, затем `task_memory`. Текущий явный запрос имеет
приоритет над working memory, а working memory конкретной задачи — над общей
long-term memory. Оба блока имеют `CompactionPolicy::Exclude`: они не попадают
напрямую в запрос summary-компактера. Это структурная гарантия для system-блоков:
факты, которые пользователь или ассистент повторил в обычных репликах, могут
попасть в conversation summary. `/forget` удаляет только durable-запись и не
стирает уже сохранённые реплики или summary. Предыдущий conversation summary
имеет `Include`, чтобы следующий summary был накопительным.

При `debug.log_payloads = false` JSONL-лог показывает безопасные метаданные
блоков — `name`, `scope`, `compaction` — и размеры сообщений, но не их текст и
не значения памяти. Включение `log_payloads = true` добавляет содержимое
запросов и может раскрыть чувствительные данные.

Общий интерфейс context provider + policy-bearing `SystemBlock` оставил шов,
который Day 12 использует для `user_profile`. Следующими provider-ами могут
стать task state (Day 13), invariants (Day 14) и transition policy (Day 15).

Пошаговый сценарий записи и SQLite/debug-проверки находятся в
[`docs/day11-results.md`](docs/day11-results.md).

## День 10: стратегии управления контекстом

Стратегия выбирается обязательным полем `context.strategy`. Доступны четыре
режима:

- `summary` — поведение Day 9: накопительное summary старой части и дословный
  хвост из N сообщений;
- `sliding_window` — только последние N сообщений без служебного LLM-вызова;
- `sticky_facts` — отдельный JSON key-value с важными фактами и последние N
  сообщений;
- `branching` — полная история активной ветки и команды для независимых
  продолжений.

SQLite во всех режимах сохраняет полную исходную историю. Sliding window
«отбрасывает» старые сообщения только из payload модели: это не удаляет данные и
не мешает восстановлению или последующему ветвлению. В N входит текущий вопрос.

### Общий SystemContext

Base prompt, summary, facts и служебные данные представлены отдельными
именованными `SystemBlock` внутри общего `SystemContext`:

```text
SystemContext blocks → выбранные user/assistant messages
```

Эти блоки не записываются как обычные реплики и не попадают под sliding window.
Начиная с Day 11, каждый блок явно задаёт scope и compaction policy: предыдущий
summary включается в следующий compaction, а base, facts и durable memory из
него исключаются.

### Sticky facts

После каждого сообщения пользователя и до основного ответа агент делает
отдельный детерминированный вызов DeepSeek. Updater получает прежний JSON и
необработанные пользовательские сообщения, но не предложения ассистента. Он
возвращает строгий объект `string → string`; затем facts передаются основному
ответу отдельным system-блоком.

Ошибка API или невалидный JSON не лишает пользователя ответа: агент использует
предыдущие facts и raw-window. Граница памяти не сдвигается, поэтому следующий
успешный updater обработает все пропущенные пользовательские сообщения. Ошибка
сохранения корректных facts в SQLite остаётся фатальной.

### Ветки

В режиме `branching` после хотя бы одного завершённого хода выполните:

```text
you> /branch
Checkpoint 2: dialog #1 remains active; created branch #2.
```

Текущий диалог остаётся первой веткой, а новая запись SQLite — его физическая
копия в точке checkpoint. Продолжите оригинал, затем переключитесь:

```text
you> /switch 2
Switched to branch #2.
```

История выбранной ветки повторно выводится в терминал. Дальнейшие сообщения и
usage двух диалогов независимы. Переключиться можно только на диалог из той же
branch group. В остальных стратегиях `/branch` и `/switch` возвращают локальную
ошибку и не вызывают DeepSeek.

### Настройки и статистика

```toml
[context]
strategy = "summary" # summary | sliding_window | sticky_facts | branching
keep_last_messages = 10
compact_after_prompt_tokens = 6000
summary_max_tokens = 1024
facts_max_tokens = 512

[debug]
# log_path = "deepseek-debug.jsonl"
log_payloads = false
```

Чтобы переключить режим, укажите ровно одно из четырёх значений:

```toml
strategy = "summary"
strategy = "sliding_window"
strategy = "sticky_facts"
strategy = "branching"
```

Это перечень допустимых вариантов, а не один валидный блок: в реальном
`[context]` должна остаться только одна строка `strategy`.

Параметры можно оставить вместе и менять только `strategy`. Summary использует
порог и `summary_max_tokens`; sticky facts использует `facts_max_tokens`;
branching не сокращает историю.

`/stats` показывает стратегию, фактическое число raw-сообщений в контексте,
границы summary/facts, активную branch group и три отдельные категории расхода:

```text
Стратегия · sticky_facts
Контекст · полная история: 8 · в запросе: 3 · facts: 2 · facts до: 7
Ответы · вход: 12000 · выход: 2000 · всего: 14000
Summary · вход: 0 · выход: 0 · всего: 0
Facts · вход: 3000 · выход: 300 · всего: 3300
API всего · 17300
```

Отсутствующий provider usage отмечается отдельно и не считается нулём. Footer
внизу чата по-прежнему относится только к последнему обычному ответу.

Сценарий и таблица для одинакового 10–15-сообщенческого сравнения находятся в
[`docs/day10-results.md`](docs/day10-results.md). Значения качества и токенов
заполняются только после реальных запусков.

### Диагностика

JSONL debug-log содержит активную стратегию, имена системных блоков, выбранное
число сообщений, границы summary/facts, служебные facts-события и операции с
ветками. Содержимое сообщений записывается только при `log_payloads = true`;
это может раскрыть чувствительный текст. API-ключ редактируется всегда.

## День 8: токены из API

Пока ожидается первый текст ответа, в строке статуса отображается «Думаю…».
В iTerm2 справа от текста проигрывается GIF белой лошади на чёрном фоне высотой в одну
текстовую строку. Файл встроен в исполняемый файл; дополнительные программы
и файлы из Downloads для запуска не нужны. При появлении первого непустого
фрагмента ответа или завершении запроса индикатор убирается.
Статистика токенов появляется только после завершения ответа.

В других терминалах, внутри tmux/screen и в очень узком окне используется
текстовый индикатор. При перенаправлении вывода индикатор отключён.
`NO_COLOR=1` отключает оформление текста, но сохраняет анимацию в iTerm2.

Внизу чата, над приглашением ввода, отображается одна общая строка
статистики последнего запроса (приглушённая в цветном терминале):

```text
Токены · Вход: 2400 · Выход: 350 · Всего: 2750
```

- **Вход** — `prompt_tokens`: system prompt, вся переданная история и новый вопрос.
- **Выход** — `completion_tokens`: генерация модели, включая рассуждения,
  если они входят в статистику провайдера.
- **Всего** — `total_tokens` из API. Это расход одного вызова,
  не сумма всех прошлых запросов и не размер сохранённой истории.
- Если API прислал `completion_tokens_details.reasoning_tokens`, рядом показано
  «Рассуждения». Это часть выхода, повторно к итогу она не прибавляется.

Во время ожидания и печати ответа статистика токенов скрыта; после
завершения появляются свежие счётчики. Перед следующим сообщением прежняя строка
убирается. При восстановлении диалога статистика появляется один раз внизу,
без подписей под старыми ответами. В узком окне строка обрезается с многоточием,
чтобы не занимать несколько рядов. Если API не прислал usage, показано **«нет данных API»**.
Нулевые значения отображаются только когда API действительно вернул нули.
Повторные события usage заменяют предыдущие значения для текущего вызова,
не суммируются. Старые показатели не переносятся на новый запрос или ошибку.

Статистика сохраняется вместе с полным ответом в одной транзакции SQLite
и восстанавливается при `--resume-last` / `--resume ID`.
При перенаправлении вывода обновления строки отключены: выводится только
одна итоговая строка при выходе, без управляющих последовательностей терминала. Для баз седьмого дня
автоматически создаётся дополнительная таблица `message_usage`; старые сообщения
сохраняются; если последняя реплика не содержит usage, строка показывает «нет данных API». Метаданные токенов не отправляются
модели как часть истории. Если незавершённый запрос успел вернуть usage, она
выводится для этого вызова, но без завершённого ответа в базу не записывается.

Раздельных счётчиков для нового вопроса и прошлой истории пока нет: API возвращает
их общий вход. Локального приблизительного подсчёта по символам здесь нет.
Флаг `include_usage` в конфигурации по умолчанию включён.
[Описание usage в DeepSeek API](https://api-docs.deepseek.com/api/create-chat-completion/).

## Сохранение и восстановление диалогов

```bash
cargo run                         # Новый диалог
cargo run -- --user alice --task telegram-bot # Новый scoped-диалог
cargo run -- --resume-last         # Продолжить последний активный диалог
cargo run -- --list-dialogs        # Список: ID, user, task, время UTC, сообщения, первый вопрос
cargo run -- --resume 3            # Продолжить диалог с ID 3
cargo run -- --db /path/chats.sqlite3 --resume-last
```

По умолчанию база — `dialogs.sqlite3` **в текущем рабочем каталоге**.
Для общей истории при запуске из разных каталогов передавай один абсолютный
путь через `--db`. Родительский каталог должен существовать. SQLite встроена
в приложение; отдельный сервер базы данных не нужен. База и её служебные
файлы исключены из Git.

Каждый обычный запуск начинает новый диалог. Запись о нём создаётся с первым
непустым сообщением; запуск и выход без сообщений не засоряют список.
`--resume-last` выбирает диалог с последней сохранённой репликой, а не просто
последний созданный. При восстановлении предыдущие сообщения выводятся
в том же окне, и можно продолжать ввод. Если диалогов нет, флаг выдаёт понятную
ошибку; запусти программу без него. `--list-dialogs` работает без API-ключа и
конфигурационного файла. Флаги списка и восстановления несовместимы друг с другом.

Сообщения сохраняются инкрементально, отдельными транзакциями:

1. Вопрос пользователя записывается **до отправки запроса в API**.
2. Полный непустой ответ записывается после успешного завершения потока.
3. Полная история остаётся сохранённой, а состав API-запроса определяет
   `context.strategy`: полный диалог, raw-window либо служебный system-блок с
   summary/facts и непокрытый хвост.

При ошибке API или принудительном завершении процесса уже записанный вопрос
остаётся в базе. Частичный, пустой или обрезанный ответ в историю не попадает:
отображение фрагмента на экране ещё не означает сохранение полного сообщения.
Запись не откладывается до выхода из программы. Ошибка базы останавливает
программу с сообщением об ошибке. Если другой процесс успел изменить тот же
диалог, устаревшая сессия также останавливается с предложением восстановить её.

`/clear` очищает текущий контекст и отсоединяет агента от старого диалога;
старые сообщения остаются в базе, следующий вопрос создаст новый диалог.
System prompt при очистке сохраняется.

## Агент в коде

`Agent` в `src/agent.rs` владеет API-клиентом, историей и необязательным
`DialogStore`. `DialogStore` в `src/dialog.rs` отвечает за SQLite.

```rust
use deepseek_cli::{agent::Agent, config::Config, dialog::DialogStore};
use std::path::Path;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = Config::load(
        Path::new("deepseek.toml"),
        std::env::var("DEEPSEEK_API_KEY").ok(),
    )?;
    let path = Path::new("dialogs.sqlite3");
    let store = DialogStore::open(path)?;
    let mut agent = Agent::with_store(&config, store)?
        .with_prompt("Объясни ownership в Rust");
    println!("{}", agent.run().await?);
    let id = agent.dialog_id().expect("Первое сообщение сохранено");
    drop(agent);

    let store = DialogStore::open(path)?;
    let mut agent = Agent::from_dialog(&config, store, id)?;
    println!("{}", agent.run_with_prompt("Теперь покажи пример").await?);
    Ok(())
}
```

- `Agent::with_store(...)` создаёт агента с сохранением сообщений.
- `Agent::from_dialog(config, store, id)` восстанавливает исходный system prompt
  и сообщения. API-ключ, модель и параметры запросов берутся из текущего конфига;
  настройки подключения и ключ не записываются в таблицы диалогов.
- `run()` использует промпт, заданный через `with_prompt(...)`;
  `run_with_prompt(...)` отправляет новое сообщение, сохраняя промпт по умолчанию.
- `run_streaming(prompt, callback)` передаёт `AgentEvent`: фрагменты ответа,
  usage, события summary-компактинга, обновления facts и ошибок debug-log.
- `branch_dialog()` создаёт checkpoint-копию активного сохранённого диалога;
  `switch_branch(id)` переключает агента на диалог из той же branch group.
- `history().messages()` возвращает сохранённые реплики для чтения;
  `message.usage()` — статистику вызова, создавшего ответ.
- `last_usage()` — последняя полученная статистика текущего запроса;
  после восстановления берётся из последней реплики, если она содержит usage.
- `context_stats()` — полная граница контекста и накопленный расход обычных и
  служебных вызовов.
- `Agent::new(...)` остаётся вариантом без базы, как в шестом дне:
  он хранит в памяти только успешно завершённые пары сообщений.

Пустые промпты отклоняются до записи и вызова API. Полная история остаётся
доступной через `history()` независимо от выбранной стратегии.

## Настройка

Создайте локальный конфиг из примера:

```bash
cp deepseek.example.toml deepseek.toml
```

Вставьте API-ключ в `api_key`. Файл `deepseek.toml` исключён из Git, однако его
всё равно следует считать секретным и не пересылать другим людям.

Ключ также можно передать переменной окружения; она имеет приоритет над файлом:

```bash
DEEPSEEK_API_KEY='your-key' deepseek-cli
```

Доступные параметры:

```toml
api_key = "replace-with-your-key"
base_url = "https://api.deepseek.com"
model = "deepseek-v4-flash"
system_prompt = "You are a helpful assistant."
temperature = 1.0
max_tokens = 4096
timeout_seconds = 120

[context]
strategy = "summary"
compact_after_prompt_tokens = 6000
keep_last_messages = 10
summary_max_tokens = 1024
facts_max_tokens = 512

[debug]
# log_path = "deepseek-debug.jsonl"
log_payloads = false
```

API-ключ обязателен в файле или `DEEPSEEK_API_KEY`, а `context.strategy` — в
файле конфигурации. Остальные поля необязательны и принимают показанные значения
по умолчанию. Другой файл можно выбрать явно:

```bash
deepseek-cli --config /path/to/config.toml
```

## Использование

```text
$ deepseek-cli
you> Объясни ownership в Rust одним абзацем
assistant> ...ответ появляется постепенно...
you> /exit
```

Команды:

- `/clear` — начать новый диалог, сохранив прежний в базе;
- `/stats` — показать контекст и накопленные токены без вызова API;
- `/remember user KEY VALUE` — явно сохранить long-term запись;
- `/remember task KEY VALUE` — явно сохранить working запись;
- `/forget user KEY` / `/forget task KEY` — удалить запись выбранного слоя;
- `/memory` — показать Conversation, Working и Long-term без вызова API;
- `/memory user` / `/memory task` — показать один durable-слой;
- `/branch` — создать checkpoint-копию активного диалога (только `branching`);
- `/switch ID` — перейти на ветку из той же группы (только `branching`);
- `/exit` или `/quit` — выйти;
- Ctrl+D — выйти.

Если запрос оборвался или API вернул ошибку, вопрос остаётся в истории,
а незавершённый ответ не сохраняется. Можно написать следующее сообщение: например,
«Ответь на предыдущий вопрос». Оно отправится вместе с сохранённым контекстом.

Цвета автоматически отключаются при перенаправлении вывода. В интерактивном
терминале их можно отключить вручную стандартной переменной `NO_COLOR`:

```bash
NO_COLOR=1 deepseek-cli
```
